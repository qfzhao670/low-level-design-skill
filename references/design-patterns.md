# 设计模式目录

18 个常用设计模式速查。每个模式给出：**意图（Intent）/ 识别信号（何时用）/ 解决什么 / 常见误用（何时不该用）**。

> 关键心态：模式是"识别问题 → 套用标准解法"的词汇表，不是待办清单。先有坏味道，再选对应模式；用不上就回到朴素写法。

## 坏味道 → 模式快速对照表

| 你遇到的坏味道 | 可能的解法 |
| --- | --- |
| 一长串 `if-else`/`switch` 按类型分发算法 | Strategy |
| 状态相关的一大堆 `if` 判断 | State |
| 一个对象变化要联动更新多个对象 | Observer |
| 想复用已有类/库，但接口对不上 | Adapter |
| 想给对象动态叠加可选行为、组合爆炸 | Decorator |
| 要控制对对象的访问（懒加载/权限/缓存） | Proxy |
| 树形结构，叶子与容器需一视同仁 | Composite |
| 客户端要跟很多子系统/服务打交道 | Facade |
| 构造参数太多、可选参数多 | Builder |
| 创建逻辑分散、按类型选择要 new 哪个类 | Factory Method |
| 一族相关对象需成组切换 | Abstract Factory |
| 全局唯一实例（谨慎） | Singleton |
| 需要复制/保存对象状态 | Prototype / Memento |
| 撤销/重做、排队、调度操作 | Command |
| 多个类流程相同、仅个别步骤不同 | Template Method |
| 要遍历自定义集合 | Iterator（通常语言已内置） |
| 多对象网状两两通信 | Mediator |

## Creational（创建型）

### Singleton（单例）
- **意图**：保证一个类全局只有一个实例，并提供全局访问点。
- **识别信号**：需要全局唯一资源（数据库连接、配置、日志、线程池）；多处各自 `new` 同一资源导致状态不一致或资源浪费。
- **解决**：统一实例，避免状态分裂与重复开销。
- **常见误用**：全局可变状态（global mutable state）会让测试困难、隐藏依赖；现代更推荐用依赖注入（DI）把"只有一个实例"的对象作为普通对象注入，而不是类内部写死 `getInstance()`。注意线程安全的实现。

### Factory Method（工厂方法）
- **意图**：把对象创建逻辑集中，让调用方不直接 `new` 具体类。
- **识别信号**：代码里到处 `new` 具体类型；创建逻辑有分支（按类型/配置选择要建哪个类）；新类型不断加入导致调用方跟着改。
- **解决**：新增类型只需改工厂，调用方依赖抽象。
- **常见误用**：只有一个产品类型、创建无任何逻辑时，工厂是多余的一层。先从一个简单工厂函数开始，别一上来就建 Factory 类层级。

### Abstract Factory（抽象工厂）
- **意图**：创建"一族相关对象"（如一套 UI 组件、一套菜系套餐），保证家族内对象搭配一致。
- **识别信号**：需要成组切换（多平台 UI、多数据库、多菜系），且各组内部成员必须配套。
- **解决**：换一个工厂就换一整套产品族。
- **常见误用**：只有单个产品、构不成"族"时用它纯属过度。别与 Factory Method 混淆——Abstract Factory 产的是**一族产品**，Factory Method 产的是**单个产品**。

### Builder（建造者）
- **意图**：分步骤构造参数很多（尤其大量可选参数）的复杂对象。
- **识别信号**：构造器参数过长、多个参数可选、构造逻辑分支复杂、靠大量重载/关键字参数拼装。
- **解决**：用链式/分步调用清晰拼装，避免"参数地狱"。
- **常见误用**：参数只有两三个时用 Builder 是负担。很多语言自带具名参数 / keyword args / 数据类，优先用语言特性。

### Prototype（原型）
- **意图**：通过克隆现有对象创建新对象，避免昂贵/复杂的重新构造。
- **识别信号**：需要保存/复制对象状态（撤销、保存点、棋盘/文档快照）；对象构造成本高且已有相近实例。
- **解决**：用 `clone()` 快速复制，注意 shallow copy（浅拷贝，共享引用）与 deep copy（深拷贝，复制真实对象）的取舍。
- **常见误用**：普通简单对象直接 `new` 或复制构造即可，不必引入 clone 协议；深拷贝易踩"引用被共享"的坑，要先明确语义。

## Structural（结构型）

### Adapter（适配器）
- **意图**：让两个接口不兼容的对象能协作，做一个"转接头"。
- **识别信号**：想复用已有类/第三方库，但它的接口和你代码期望的接口对不上（如换用 SendGrid 邮件服务）。
- **解决**：写一层 Adapter 把目标接口翻译成已有接口，两边都不改。
- **常见误用**：两个接口本来就一致就别包一层；能改其中一边接口时，直接改可能更省事。

### Decorator（装饰器）
- **意图**：在运行时给对象动态叠加行为，且不改变原对象。
- **识别信号**：想给对象加多种可选能力（加料、加日志、加缓存），用子类组合导致类数量爆炸。
- **解决**：用包装（wrap）按需叠加，替代"为每种组合建一个子类"。
- **常见误用**：只加一种固定行为时，直接改类或加一个方法更简单；装饰层太多会难追踪调用栈。别与 Proxy 混淆——Decorator 管"加行为"，Proxy 管"访问控制"。

### Proxy（代理）
- **意图**：用一个替身对象控制对真实对象的访问。
- **识别信号**：需要懒加载、权限控制、缓存、日志、远程调用等横切关注点，且不想污染真实对象。
- **解决**：代理拦截访问，真实对象保持纯粹。
- **常见误用**：没有访问控制需求时不必上 Proxy；与 Decorator 形似，务必按"控制访问 vs 增加行为"区分。

### Composite（组合）
- **意图**：让"单个对象"和"对象组合"对客户端一视同仁（树形结构）。
- **识别信号**：代码里到处用 `if` 区分"是叶子还是容器"；需要递归处理树/层级结构（文件与文件夹、菜单与子菜单）。
- **解决**：统一接口，客户端无需区分叶子与组合。
- **常见误用**：没有真正的递归层级结构时（一堆扁平对象），Composite 是多余抽象。

### Facade（外观）
- **意图**：给一组复杂子系统提供一个简单统一的入口。
- **识别信号**：客户端要跟很多服务/模块交互、调用序列复杂、内部结构外泄（如 App 直连多个微服务）。
- **解决**：一个 Facade 封装复杂交互，客户端只依赖 Facade。
- **常见误用**：Facade 不应承担业务逻辑（否则退化成上帝类）；也别为只有一个调用的地方包 Facade。子系统本身仍可被高级用户直接使用。

## Behavioral（行为型）

### Strategy（策略）
- **意图**：把一组可互换的算法/策略各自封装，运行时选择。
- **识别信号**：一长串 `if-else`/`switch` 按类型选不同算法（折扣、支付、排序、路线）；算法需要独立测试/替换。
- **解决**：每个策略一个类，新增策略不动旧代码（顺带满足 OCP）。
- **常见误用**：策略只有两种且几乎不变时，`if-else` 可能更清晰。别为了消灭 `if-else` 而消灭 `if-else`。

### Observer（观察者）
- **意图**：一对多依赖，一个对象状态变化时自动通知所有依赖者。
- **识别信号**：一个对象变化要联动更新多个对象；新增/移除监听者要改被观察者代码。
- **解决**：发布-订阅解耦，观察者可动态注册/注销。
- **常见误用**：观察者过多、通知顺序敏感、易造成循环通知与内存泄漏（忘记注销）。简单场景可用回调/事件代替完整 Observer 框架。

### Command（命令）
- **意图**：把请求/操作封装成对象，便于参数化、排队、撤销、记录日志。
- **识别信号**：需要撤销/重做、把操作放入队列/调度、记录操作历史、或解耦"发起者（Invoker）"与"执行者（Receiver）"。
- **解决**：命令对象携带操作与参数，Invoker 无需知道 Receiver 细节。
- **常见误用**：只是普通调用时包成 Command 是多余的仪式感；撤销/队列等需求不存在就别上。

### Template Method（模板方法）
- **意图**：在父类定义算法骨架，把可变步骤留给子类实现。
- **识别信号**：多个类有几乎相同的流程，只有其中几步不同（如读文件：打开 → 解析 → 关闭，仅解析不同）。
- **解决**：骨架复用，变化点下沉到子类/钩子方法（hook）。
- **常见误用**：可变点太多或骨架本就不稳定时，Template Method 会变得僵硬，此时考虑 Strategy 或组合；继承带来的强耦合要留意。

### Iterator（迭代器）
- **意图**：提供统一方式遍历集合，而无需暴露其内部结构。
- **识别信号**：客户端要遍历自定义集合，却被迫知道其内部存储方式。
- **解决**：统一 `has_next()` / `next()` 接口遍历。
- **常见误用**：绝大多数语言内置了迭代器/生成器，别重复造轮子，直接用语言原生。

### State（状态）
- **意图**：对象行为随内部状态改变，把每个状态封装成类，消除状态判断的 `if-else`。
- **识别信号**：对象有若干状态，方法里大量 `if`/`switch` 判断当前状态决定行为（订单状态机、播放器、ATM、交通灯）。
- **解决**：每个状态一个类，状态转换显式化。
- **常见误用**：状态只有 1-2 个或转换极简单时，用枚举 + `if` 更直接；状态类太多同样难维护，需权衡。别与 Strategy 混淆——State 是"状态驱动、可自动切换"，Strategy 是"外部选择、通常不自动切换"。

### Memento（备忘录）
- **意图**：在不暴露对象内部细节的前提下，捕获并保存对象状态以便恢复（undo/redo）。
- **识别信号**：需要撤销/重做、快照、回滚，且不能直接暴露内部状态。
- **解决**：Originator 生成 Memento，Caretaker 负责保存、不碰 Memento 内部。
- **常见误用**：状态很大时快照成本高，可用 Command（增量撤销）或不可变对象替代；只为"保存一次"不必上 Memento。

### Mediator（中介者）
- **意图**：用中心对象协调多对象间的交互，避免对象间网状直接引用。
- **识别信号**：多个对象两两通信、依赖关系像蜘蛛网；加一个对象要改所有相关对象。
- **解决**：交互逻辑集中到 Mediator，对象只和 Mediator 通信。
- **常见误用**：对象很少、交互简单时，Mediator 是额外一层；Mediator 本身容易膨胀成上帝类，要留意。
